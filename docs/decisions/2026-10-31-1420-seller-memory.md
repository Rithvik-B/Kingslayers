## Context
The agent makes many choices for the seller: what the product is, who should buy it (ICP and GTM), how to
write, who to feature, how to read a reply, when to book. The seller makes choices too: approving, starring,
sending, overriding. Rithvik wants all of it documented, visible, editable, and actually used by the agents,
like a datahub or memory that the seller can tune.

## Decision
- **One `memory` table**, written through `app/memory.py` (`PLAN.md` §6.13), with a frozen key registry:
  - **knowledge:** `product.profile`, `gtm.icp`, `voice.style`, `outreach.rules`, `scheduling.prefs`,
    `reply.prefs`
  - **decisions:** `decision.*`, from both the agent and the seller, each with a rationale
- **Agents read memory at the start of every step.** A seller's edit therefore changes the next discovery
  run, draft, slot offer or reply decision.
- **A seller's edit locks that key.** Later agent output is kept only as a "proposed" suggestion, not
  applied.
- **Seller-wide knowledge carries across campaigns.** Decisions are per campaign. A demo reset keeps
  seller-wide memory.
- **The UI shows a Memory panel:** grouped knowledge with JSON edit, a decisions timeline with AGENT and YOU
  badges, and Re-run discovery and Regenerate drafts buttons.
- **It's Tier 1.** History, revert and Markdown export are Tier 2.

## Why
It makes the agent's reasoning transparent and steerable, which fits our "every claim has a receipt" angle.
The seller can see why the agent did something and change it.

## Alternatives considered
- Keep the product profile and ICP as columns on the campaign: simpler, but it can't be edited across
  campaigns, and it doesn't capture decisions.
- Markdown config files like Crustdata's ICP Builder: easy to read, but harder to edit safely from the UI and
  to version.

## Consequences
- The `campaigns.product_profile` and `campaigns.icp` columns were removed from the contract.
- P1 owns `memory.py`, its routes and the panel. P2 and P3 read and write the keys named in `PLAN.md`.
